# S3 설계 (40–50분)

## 역할
이 스킬은 합의 범위를 사람이 이해하고 설명할 수 있는 구조로 옮긴다(제출 후 서술형에서 설명해야 한다).
사람이 정하는 것: 제안 반박·선택, 결정마다 의도 문장.

## 입력
`docs/AGREEMENT.md`(제약 포함), `docs/INTERVIEW.md`의 L1·L2·L3. 번역 규칙: `.agents/skills/fde-interview/references/expertise-extraction.md` §4.
**AGREEMENT 성공 기준이 비어 있으면 시작하지 않는다** — 추측해서 채우지 말고 사용자에게 먼저 받는다.
시작할 때 `bash .agents/skills/fde-start/scripts/check-stage.sh S3`를 실행한다. 실패(exit 1)면 출력된 빈 칸을 사용자에게 보여 주고 멈춘다.

## 절차
### 0단계: 번역표부터 (5분)
| 담당자가 말한 형태 | 목적지 |
|---|---|
| "○○가 너무 많다/적다", "너무 길다/짧다", "○○면 아예 안 된다" | **고정 코드** 지표·판정 |
| "○○가 꼭 들어가야 한다" | **LLM** 판단 → 스키마 boolean |
| 출력 순서·개수 (L2) | **스키마 필드 순서 + 화면 배치** |
| 실제 문장 (L3) | **LLM 프롬프트 어조 예시** |

**셀 수 있는 것은 전부 고정 코드로 내린다.** 비어 있는 층은 추측하지 말고 담당자 질문으로 돌려준다.

### 1단계: 제안 (코드 금지)
선택지가 갈리는 곳은 대안 1개와 트레이드오프 한 줄.
1. 화면 흐름 — 최소 개수. 사용자가 **설명 없이** 쓰도록(채점은 실행 화면을 본다):
   첫 화면에 **다음 행동 하나**(버튼 하나) / 입력 중·처리 중·실패 **세 상태**가 글자로, 실패 문구에 다시 할 방법 /
   결과는 L2 순서대로 한 화면, 바로 **다시 하기**.
2. 데이터 흐름 — 입력 → 처리 → 저장 → 표시, 단계마다 [고정 코드]/[LLM]
3. LLM 호출 — 횟수, 입출력 JSON 스키마(**필드 순서는 L2**), 실패 시 보이는 것
4. 저장 — 가장 단순한 것(파일/SQLite/메모리)과 이유
5. 의도적으로 안 하는 것 — 로그인, 권한, 확장성 등 각 한 줄 이유
6. 깨지기 쉬운 지점 3개와 확인 방법. **성공 기준마다 확인 방법**(무엇을 입력하고 화면에서 무엇을 보면 충족인지) 한 줄씩.
7. 스택 — 환경에 이미 있는 런타임 우선. 무거운 빌드는 피한다(RAM 초과 OOM은 구제 안 됨).

### 2단계: 확정 (사람이 반박·수정한 뒤)
- 결정마다 DECISIONS 5줄. **의도**는 결정마다 한 줄로 묻고 답을 그대로 적는다 — ID만 가리키지 않고
  그 결정의 "선택" 한 줄을 다시 보여준다(사람이 Codex·담당자 세션을 오가며 기억이 끊긴 상태일 수 있다):
  "D○(<선택 한 줄>)로 지키려는 것과 일부러 포기한 것을 한 줄로 말해 주세요."
- 사람이 네 제안을 바꿨으면 "내가 바꾼 제안" 표에 한 줄(네 제안 / 사람이 고른 것 / 사람이 말한 이유).
- AGREEMENT 성공 기준 표의 "확인 방법" 열을 채운다.
- STATE 작업 목록: 한 번에 끝낼 수 있는 최소 단위(**리프 항목**, 20분 이하)로 쪼갠다. 첫 항목은 "가짜 데이터로라도 처음→끝 한 번
  흐르게 하기", 결정론 코어 테스트 1개 포함. 항목마다 **완료 조건**(실행해서 무엇이 보이면 끝인가)과 **연결된 성공 기준 번호**를 붙인다.
  - 빠짐없이: 모든 성공 기준 번호가 어느 항목에든 한 번 이상 나온다.
  - 겹치지 않게: 두 항목이 같은 일을 하지 않는다. 항목마다 주로 바꿀 파일이 다르다.
  기준판 "다음 작업"에 첫 항목.

## 출력
```text
파일: docs/DECISIONS.md D1… (선택 / 이유 / 의도 / 버린 대안 / 알려진 약점), "내가 바꾼 제안" 표,
      docs/AGREEMENT.md "확인 방법" 열, docs/STATE.md 작업 목록·기준판 다음 작업, 커밋 [S3] docs: 설계 결정
```
작업 목록 한 줄: - [ ] <항목> — 완료 조건: <실행해서 보이는 것> — 성공 기준 #n[,#m] (E2E·테스트 항목은 "—")
불변 조건: 결정마다 정확히 5줄. 의도 칸은 사람 말 그대로이거나 `empty`(지어내지 않는다). 작업 목록 첫 항목은 E2E.
작업 목록 항목마다 완료 조건이 있고, 성공 기준 번호가 하나도 빠지지 않는다.

## 원칙
1. 이유 칸은 AGREEMENT 항목 또는 INTERVIEW 번호를 가리킨다.
2. 화면·스키마 순서는 L2 인용을 따른다.

## 금지사항
- 코드를 쓰지 않는다.
- AGREEMENT "만들 것"에 없는 구조(인증, 범용 저장소, 확장용 추상화)를 제안하지 않는다. AGREEMENT "제약"을 어기는 저장·전송을 제안하지 않는다.
- 의도 칸을 추측으로 채우지 않는다.

## 확인요청
- AGREEMENT 성공 기준이 비었다 → 자동으로 채우지 않고 사용자에게 받는다.
- 번역표에서 비어 있는 층 → 담당자 질문으로 돌려준다.
- 결정마다 의도 한 줄을 묻는다.

## 예시
### 입력
```
INTERVIEW L1 인용: "45초 넘으면 너무 길어요." / 사람: "D1 좋아요. 길이는 화면에 숫자로 보여 주고 싶어요, 선수가 바로 알게."
```
### 출력
```text
## D1. 답변 길이 판정은 고정 코드
- **선택**: STT 결과의 시간 길이로 45초 초과를 코드로 판정, 결과 화면에 초 단위 숫자 표시
- **이유**: INTERVIEW #4 L1 "45초 넘으면 너무 길어요" — 셀 수 있는 기준
- **의도**: 선수가 바로 알게 숫자로 보여 주고 싶다 / (포기한 것: empty — 물어볼 것)
- **버린 대안**: LLM에게 길이 평가를 맡김 — 같은 답에 결과가 흔들린다
- **알려진 약점**: 녹음 앞뒤 무음도 길이에 들어간다 — 무음 10초 녹음으로 확인
```

## 인접 스킬
- vs `$fde-build`: 이 스킬은 결정과 작업 목록까지, 코드는 build가 항목 하나씩.
- 선택: 담당자 기준을 옮긴 직후 되읽기 확인 1회는 `$fde-agreement` 템플릿 1-B.
- **병렬(선택)**: 결정 하나의 의도를 사람에게 묻고 답을 받는 동안, 이미 확정된 결정의 `DECISIONS.md` 5줄·작업 목록
  리프 항목 정리는 **보조 세션**에 맡길 수 있다(`docs/kit/eval` 연습과 달리 같은 작업 폴더 파일을 직접 쓰게 한다).
  메인은 그 사이 다음 결정의 제안을 준비하거나 S4 첫 항목을 미리 가늠한다. 한 결정의 5줄은 메인·보조 둘 중 하나만 쓴다.

## 완료
- 모든 결정에 5줄이 있고, 성공 기준마다 확인 방법이 있고, 작업 목록 첫 항목이 E2E다. 50분이 되면 의도가 빈 결정은 번호만 남기고 S4로.
- 자가 검증: DECISIONS 이유 칸이 모두 AGREEMENT·INTERVIEW를 가리키고, AGREEMENT "확인 방법"에 빈 행이 없다.
  `bash .agents/skills/fde-start/scripts/check-stage.sh S4`가 통과한다(확인 방법·작업 목록 완료 조건 누락을 잡는다).
