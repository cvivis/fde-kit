# S3 설계

## 역할
이 스킬은 합의 범위를 사람이 이해하고 설명할 수 있는 구조로 옮긴다(제출 후 서술형에서 설명해야 한다).
사람이 정하는 것: 제안 반박·선택, 결정별 의도 문장(한 번에 묶어 답한다).

## 입력
`docs/AGREEMENT.md`의 한 줄 명세·만들 것·제약·성공 기준·가정, `docs/INTERVIEW.md`의 "정리"·"요구 체크리스트"(기기·입력 크기·저장·실패 처리 값은 여기서 가져오고, `— 가정`인 값은 제안에 "(가정)"으로 표시). 번역 규칙: `.agents/skills/fde-interview/references/expertise-extraction.md` §4.
`docs/REQ-TASK.md`·`docs/REQ-USER.md`는 범위 "이번" 행의 ID·요구·종류만 읽는다(설계 연결 칸을 채울 때).
**AGREEMENT 성공 기준이 비어 있으면 시작하지 않는다** — 추측해서 채우지 말고 사용자에게 먼저 받는다.
시작할 때 `bash .agents/skills/fde-start/scripts/check-stage.sh S3`를 실행한다. 실패(exit 1)면 출력된 빈 칸을 사용자에게 보여 주고 멈춘다.

## 절차
### 0단계: 번역표부터
| 담당자가 말한 형태 | 목적지 |
|---|---|
| "○○가 너무 많다/적다", "너무 길다/짧다", "○○면 아예 안 된다" | **고정 코드** 지표·판정 |
| "○○가 꼭 들어가야 한다" | **LLM** 판단 → 스키마 boolean |
| 출력 순서·개수 (L2) | **스키마 필드 순서 + 화면 배치** |
| 실제 문장 (L3) | **LLM 프롬프트 어조 예시** |

**셀 수 있는 것은 전부 고정 코드로 내린다.** 비어 있는 층은 추측하지 말고 담당자 질문으로 돌려준다.

### 0-B단계: 결정 로직 (`docs/LOGIC.md`)
규칙이 걸린 **결정**(정하기·계산·판정·고르기) 하나를 골라 적는다. 로그인·저장·화면 같은 기능은 적지 않는다.
결정이 없으면 `- 결정: 결정 없음 — <이유>` 한 줄로 끝낸다.
1. **결정 한 문장 + 출력 한 줄**: 무엇을 누구에게 정해 주는가, 결과 한 줄은 어떤 모양인가.
2. **조건 3종**: 번역표의 고정 코드 기준을 반드시(어기면 결과를 못 씀)·점수(작을수록 좋음)·목표(전체로 줄임)로 나눠 숫자 규칙으로 적는다.
   숫자가 없으면 지어내지 않는다. 규칙 칸에 `숫자 없음 — 질문`이라 적고, 확정 질문에 묶어 담당자 질문으로 돌린다.
   담당자에게 물어 숫자를 받으면 그 답을 **INTERVIEW 대화 기록에 새 행(인용)으로 추가**하고 조건 표 근거 칸에 그 번호를 적는다(근거 원본은 INTERVIEW 하나).
   **범위는 인용 그대로** 옮긴다. "제일 바쁜 시간대"를 "오전 9시"로 좁히지 않는다. 좁혀야 하면 AGREEMENT 가정에 적고 확정 질문에 넣는다.
3. **단계**: 단계 하나 = 고정 코드 함수 하나. 바꾸기 어려운 결정(위치·그룹)을 앞에 둔다. 표는 실행 순서대로.
   단계마다 **고르는 규칙**(정렬 기준·동점 처리·한도)을 적는다. "적절히 배정"처럼 읽는 사람이 따라 할 수 없는 말은 쓰지 않는다.
   **확인 케이스**는 손으로 계산할 수 있는 작은 입력과 기대 출력이다. 테스트 이름은 S4에서 채운다.
   **손으로 따라가는 예시**: 실제 데이터 1~2건을 단계 순서대로 따라간 기대값을 적는다.
4. **배정표**: 조건마다 담당 단계와 방식(만들면서 지킴 / 검사 후 고침)을 적는다. 담당 없는 "반드시"가 남으면 S3를 끝내지 않는다.
5. **검사기**: 반드시·점수 조건을 판정하는 함수 하나. 출력에 검사한 수와 위반 수를 따로 보인다(`검사 n건 … / 위반 m건` — 스크립트가 이 글자를 읽는다). 검사 0건은 실패다.
   **위반 테스트 표**: 반드시 조건마다 일부러 어긴 작은 입력 하나와 기대(위반 1건 이상)를 적는다. 테스트 이름은 S4에서 `C<n> 위반 — …`로 만든다.

### 1단계: 제안 (코드 금지)
선택지가 갈리는 곳은 대안 1개와 트레이드오프 한 줄.
1. 화면 흐름 — 최소 개수. 사용자가 **설명 없이** 쓰도록(채점은 실행 화면을 본다):
   **화면(단계)마다 한 가지 일** — 지금 할 행동 1개와 그에 필요한 정보만 보인다. 기록·설정·도움말은 접거나 다른 화면으로.
   첫 화면에 **다음 행동 하나**(버튼 하나) / 입력 중·처리 중·실패 **세 상태**가 글자로, 실패 문구에 다시 할 방법 /
   결과 화면은 L2 순서대로 **결과만**, 바로 **다시 하기**. 한 페이지 안에서 단계별로 보이고 숨겨도 된다(페이지를 꼭 나눌 필요 없음).
   제안은 표로: `화면 · 할 일 1개 · 보이는 것(최대 3묶음) · 숨기는 것`. 결과 항목이 L2로 4개 이상이면 결과 화면만 예외.
2. 데이터 흐름 — 입력 → 처리 → 저장 → 표시, 단계마다 [고정 코드]/[LLM]
3. LLM 호출 — 횟수, 입출력 JSON 스키마(**필드 순서는 L2**), 실패 시 보이는 것
4. 저장 — 가장 단순한 것(파일/SQLite/메모리)과 이유
5. 의도적으로 안 하는 것 — 로그인, 권한, 확장성 등 각 한 줄 이유
6. 깨지기 쉬운 지점 3개와 확인 방법. **성공 기준마다 확인 방법**(무엇을 입력하고 화면에서 무엇을 보면 충족인지) 한 줄씩.
7. 스택 — 환경에 이미 있는 런타임 우선. 무거운 빌드는 피한다(RAM 초과 OOM은 구제 안 됨).

### 2단계: 확정 (사람이 반박·수정한 뒤)
- 제안과 함께 `결정 ID | 선택 요약 | 지킬 것·포기할 것(사람 답)` 표를 한 번 보여 준다. **설계 선택·의도·작업 목록 승인**을
  한 번에 묻는다. 이미 사람이 이유를 말한 결정은 원문으로 채우고 다시 묻지 않는다. 답이 빠진 결정만 모아 후속 질문 1회.
- 결정마다 DECISIONS 5줄, 각 칸은 한 문장. **의도**는 해당 ID에 대해 받은 사람 말 그대로 적는다.
  "좋아요"만으로 의도를 추측하지 않는다. 미응답은 `empty — 미응답`으로 표시한다. 변경된 결정만 갱신한다.
  큰 JSON 스키마·번역표는 한 곳에만 두고 결정에서는 위치를 참조한다.
- 사람이 네 제안을 바꿨으면 "내가 바꾼 제안" 표에 한 줄(네 제안 / 사람이 고른 것 / 사람이 말한 이유).
- AGREEMENT 성공 기준 표의 "확인 방법" 열을 채운다.
- STATE 작업 목록: 한 번에 끝낼 수 있는 최소 단위(**리프 항목**, 실행 확인 한 번으로 끝나는 크기)로 쪼갠다. 첫 항목은 "**실제 입력→실제 처리→결과** 최소 E2E"이며 핵심 연결과 관련된 최소 테스트를 포함한다.
  LOGIC에 결정이 있으면 첫 항목은 **가장 단순한 방법**으로 결과까지 잇는 뼈대이고, 둘째 항목은 **검사기**(완료 조건: 출발선 `검사 n·위반 m` 기록)다.
  결과를 좋게 만드는 개선 항목은 검사기 뒤에 둔다.
  환경이 없어 모의가 필요하면 먼저 대체 범위·이유를 승인받고, 실제 연결은 미완료 후속 항목으로 남긴다. 항목마다 **완료 조건**(실행해서 무엇이 보이면 끝인가)과 **연결된 성공 기준 번호**를 붙인다.
  - 빠짐없이: 모든 성공 기준 번호가 어느 항목에든 한 번 이상 나온다.
  - 겹치지 않게: 두 항목이 같은 일을 하지 않는다. 항목마다 주로 바꿀 파일이 다르다.
  기준판 "다음 작업"에 첫 항목, "실행 승인"에 승인된 항목 ID·단계·사람의 진행 지시를 적는다.
  승인 전에는 `미승인`이다. 기본 "실행 방식"은 연속이며 사람이 이번 항목만 요청하면 단일이다.
- **요구 추적·설계 점검(설계 뒤) — 스크립트가 판정한다**: 작업 목록·LOGIC 초안을 쓰면 REQ 두 문서의 범위 "이번" 요구마다 "설계 연결" 칸에
  그 요구를 맡은 작업 항목 T<n>·LOGIC 조건 C<n>(단계 P<n>)·결정 D<n>를 적고, 한 번씩 돌린다:
  `bash .agents/skills/fde-start/scripts/check-req.sh links` — 설계 연결 누락, **숫자 대조**(요구 숫자·단위 ↔ 연결된 조건 규칙), 근거 없음(범위 밖), 해석 차이(종류)
  `bash .agents/skills/fde-start/scripts/check-work.sh design` — **출처 없는 숫자**(규칙 숫자가 INTERVIEW·가정·RESEARCH·REQ·지문에 없음), 점수 조건의 숫자 한도,
  위반 테스트 계획, 단계 고르는 규칙·예시, DECISIONS 5줄·이유 근거, 작업 목록 첫 항목 E2E·둘째 검사기.
  두 출력의 요약 줄과 `실패:`·`경고`·`숫자 불일치`·`근거 없음` 줄을 승인 질문과 **같은 묶음**에 그대로 옮긴다. 숫자·개수·연결·5줄은 손으로 다시 대조하지 않는다.
  `실패:`(반드시 숫자 불일치·출처 없는 반드시 숫자·연결 누락)는 S4로 못 간다 — 담당자 답이나 AGREEMENT 가정(값과 이유)으로 숫자 출처를 남기거나 규칙을 요구 숫자로 고친다.
  **네 판단은 스크립트가 못 보는 것만**: 요구 원문과 조건·작업 항목의 대상·조건 범위가 넓어지거나 좁아진 것(일부를 전부로, 말하지 않은 예외·필터 추가)을
  VERIFY "해석 점검"에 시점 S3로 한 행씩 적는다(스크립트의 숫자 불일치·해석 차이 줄도 같은 표에 옮긴다). 고칠지(요구에 잇기·빼기·그대로 두기)는 사람이 정하고,
  사람 판단 칸에 그 말을 그대로 적는다. 누락은 설계를 고쳐 메우거나 사람 승인으로 그 요구를 "제외 — 이유"로 돌린다.

## 출력
```text
파일: docs/DECISIONS.md D1… (선택 / 이유 / 의도 / 버린 대안 / 알려진 약점), "내가 바꾼 제안" 표,
      docs/LOGIC.md (결정·출력 한 줄 / 조건 표 / 단계 표 / 검사기, 또는 "결정 없음 — 이유" 한 줄),
      docs/AGREEMENT.md "확인 방법" 열, docs/STATE.md 작업 목록·기준판 다음 작업,
      docs/REQ-TASK.md·REQ-USER.md "설계 연결" 칸, docs/VERIFY.md "해석 점검" S3 행, 커밋 [S3] docs: 설계 결정
보고: check-req.sh links 출력 — 설계 연결: 요구 n개 중 설계 연결 m개, 누락: <ID 또는 없음> / 숫자 대조: … / 근거 없음(범위 밖): … / 해석 차이: …
      check-work.sh design 출력 — 출처 없는 숫자: … / 위반 테스트 계획: … / 실패:·경고 줄 그대로
```
조건 표 한 줄: | C<n> | 반드시|점수|목표 | <숫자 규칙 또는 "숫자 없음 — 질문"> | <INTERVIEW #·AGREEMENT 항목> | P<n> | 만들면서 지킴|검사 후 고침 |
단계 표 한 줄: | P<n> | <하는 일> | <정렬 기준 · 동점 · 한도> | <입력 → 출력> | <작은 입력 → 기대 출력 · 테스트(S4)> |
작업 목록 한 줄: - [ ] T<번호> <항목> — 완료 조건: <실행해서 보이는 것> — 성공 기준 #n[,#m] (E2E·테스트 항목은 "—")
불변 조건: 결정마다 정확히 5줄. 의도 칸은 사람 말 그대로이거나 `empty`(지어내지 않는다). 작업 목록 첫 항목은 E2E.
작업 목록 항목마다 완료 조건이 있고, 성공 기준 번호가 하나도 빠지지 않는다.
범위 "이번" 요구마다 설계 연결 칸에 실제로 있는 설계 ID가 1개 이상 있다(`check-req.sh links` exit 0). 근거 없음·해석 차이는 사람 판단이 적혀 있거나 `미응답`이다.
LOGIC "반드시" 조건마다 담당 단계와 위반 테스트 행이 있다. 규칙 숫자는 근거 문서에 있고(`check-work.sh design` 출처 없는 반드시 숫자 0), 요구 숫자와 같으며
(`check-req.sh links` 반드시 숫자 불일치 0), 조건의 범위는 인용보다 좁지 않다.
단계 행마다 고르는 규칙과 확인 케이스(입력 → 기대)가 있고, 손으로 따라가는 예시가 1건 이상 있다. 선택·의도는 DECISIONS에만 적는다.

## 원칙
1. 이유 칸은 AGREEMENT 항목 또는 INTERVIEW 번호를 가리킨다.
2. 화면·스키마 순서는 L2 인용을 따른다.

## 금지사항
- 코드를 쓰지 않는다.
- AGREEMENT "만들 것"에 없는 구조(인증, 범용 저장소, 확장용 추상화)를 제안하지 않는다. AGREEMENT "제약"을 어기는 저장·전송을 제안하지 않는다.
- 의도 칸을 추측으로 채우지 않는다.
- LOGIC 조건의 숫자를 지어내지 않고, 인용의 범위를 좁히지 않는다. 담당 단계가 없는 "반드시" 조건을 남긴 채 S4로 넘기지 않는다.

## 확인요청
- AGREEMENT 성공 기준이 비었다 → 자동으로 채우지 않고 사용자에게 받는다.
- 번역표에서 비어 있는 층, LOGIC 조건의 `숫자 없음` → 확정 질문에 묶어 담당자 질문으로 돌려준다.
- 선택 요약·의도·작업 목록 승인을 한 번에 묻고, 이미 받은 답은 재질문하지 않는다.
- 설계 연결 누락·근거 없음(범위 밖)·해석 차이 → 같은 묶음에 넣어 보여 주고, 고칠지는 사람이 정한다(네가 지우거나 범위를 바꾸지 않는다).

## 예시
### 입력
```
INTERVIEW L1 인용: "45초 넘으면 너무 길어요." / 사람: "D1 좋아요. 길이는 화면에 숫자로 보여 주고 싶어요, 선수가 바로 알게."
```
### 출력
```text
## D1. 답변 길이 판정은 고정 코드
- **선택**: STT 결과의 시간 길이로 45초 초과를 코드로 판정, 결과 화면에 초 단위 숫자 표시
- **이유**: INTERVIEW #4 L1 "45초 넘으면 너무 길어요" — 셀 수 있는 기준
- **의도**: 선수가 바로 알게 숫자로 보여 주고 싶다 / (포기한 것: empty — 물어볼 것)
- **버린 대안**: LLM에게 길이 평가를 맡김 — 같은 답에 결과가 흔들린다
- **알려진 약점**: 녹음 앞뒤 무음도 길이에 들어간다 — 무음 10초 녹음으로 확인
```

## 인접 스킬
- vs `$fde-build`: 이 스킬은 결정과 작업 목록까지, 코드는 build가 항목 하나씩.
- 선택: 담당자 기준을 옮긴 직후 되읽기 확인 1회는 `$fde-agreement` 템플릿 1-B.
- 짧은 결정 기록은 메인에서 바로 한다. 독립적인 긴 조사만 필요할 때 보조에 맡기며, 문서 정리만을 위한 새 세션은 기본으로 열지 않는다.

## 완료
- 모든 결정에 5줄이 있고, 성공 기준마다 확인 방법이 있고, 작업 목록 첫 항목이 E2E다. 사람이 답하지 않고 넘기라고 한 의도는 `empty — 미응답`으로 남긴다. 승인된 작업만 S4로 넘기며 미승인 설계를 자동 확정하지 않는다.
- 승인과 진행 지시를 함께 받았으면 확정 기록 후 `$fde-build`로 이어 간다. 같은 승인을 다시 기다리지 않는다.
- STATE 진행 측정에 S3 종료 시각·확인 가능한 토큰을 한 행 남긴다.
- 자가 검증은 스크립트로 한다: `bash .agents/skills/fde-start/scripts/check-stage.sh S4`가 통과한다(확인 방법·작업 목록 완료 조건 누락, LOGIC 결정·조건 0개·
  반드시 조건 담당 누락, 요구 설계 연결 누락·반드시 숫자 불일치, 출처 없는 반드시 숫자를 막고, check-work.sh design의 경고 — DECISIONS 이유 근거·5줄 등 — 를 함께 낸다).
  exit 3(실행 불가 — node 없음)은 통과가 아니다. 남은 경고는 승인 묶음에 넣었는지만 본다.
