# S3 설계 (43–55분)

코드는 쓰지 않는다. 사람이 이해하고 설명할 수 있는 구조만 채택한다(제출 후 서술형에서 설명해야 한다).

## 0단계: 번역표부터 (5분)
`docs/INTERVIEW.md`의 **L1 기준 / L2 순서 / L3 문장**을 구현 위치로 보낸다.
규칙과 표: `.agents/skills/fde-interview/references/expertise-extraction.md` §4

| 담당자가 말한 형태 | 목적지 |
|---|---|
| "○○가 너무 많다/적다", "너무 길다/짧다", "○○면 아예 안 된다" | **고정 코드** 지표·판정 |
| "○○가 꼭 들어가야 한다" | **LLM** 판단 → 스키마 boolean |
| 출력 순서·개수 (L2) | **스키마 필드 순서 + 화면 배치** |
| 실제 문장 (L3) | **LLM 프롬프트 어조 예시** |

**셀 수 있는 것은 전부 고정 코드로 내린다.** 이 경계를 먼저 정하면 아래 1~7이 거의 자동으로 나온다.
비어 있는 층이 있으면 추측하지 말고 "담당자에게 물을 질문"으로 돌려준다.

## 1단계: 제안 (코드 금지)
`docs/AGREEMENT.md` 범위와 위 번역표만으로 아래를 제안한다.
선택지가 갈리는 곳은 대안 1개와 트레이드오프 한 줄.
1. 화면 흐름 — 최소 개수. 사용자가 **설명 없이** 쓰도록 세 가지를 지킨다(채점은 실행 화면을 본다):
   - 첫 화면에 **다음 행동 하나**가 가장 크게 보인다(버튼 하나).
   - 입력 중(녹음 등)·처리 중·실패 **세 상태**가 화면에 글자로 보인다. 실패 문구에 다시 할 방법을 적는다.
   - 결과는 L2 순서대로 한 화면에 보이고, 결과 화면에서 바로 **다시 하기**로 돌아간다.
2. 데이터 흐름 — 입력 → 처리 → 저장 → 표시, 각 단계에 [고정 코드]/[LLM] 표시
3. LLM 호출 — 횟수, 입출력 JSON 스키마(**필드 순서는 L2를 따른다**), 실패 시 보이는 것
4. 저장 — 가장 단순한 것(파일/SQLite/메모리)과 이유
5. 의도적으로 안 하는 것 — 로그인, 권한, 확장성 등 각 한 줄 이유
6. 깨지기 쉬운 지점 3개와 확인 방법
7. 스택 — 환경에 이미 있는 런타임 우선. 무거운 빌드(대형 의존성, 장시간 컴파일)는 피한다. 상단 RAM 표시를 넘기면 OOM이고 구제되지 않는다.

## 2단계: 확정 (사람이 반박·수정한 뒤)
- `docs/DECISIONS.md`에 결정마다 "선택 / 이유(합의된 어떤 요구) / 의도 / 버린 대안 / 알려진 약점" 5줄.
- **의도는 사람에게서 받는다.** 결정마다 한 줄로 묻고 답을 그대로 적는다:
  "D○로 지키려는 것과 일부러 포기한 것을 한 줄로 말해 주세요." 너의 추측으로 채우지 않는다.
- 사람이 네 제안을 반박·수정했으면 DECISIONS **"내가 바꾼 제안"** 표에 한 줄(네 제안 / 사람이 고른 것 / 사람이 말한 이유).
  이것이 개발자의 판단 기준(암묵지)이 남는 유일한 자리다.
- `docs/STATE.md` 작업 목록: 항목당 20분 이하. 첫 항목은 반드시 "가짜 데이터로라도 처음→끝 한 번 흐르게 하기". 결정론 코어에 대한 최소 테스트 1개 항목 포함.
- 커밋: `[S3] docs: 설계 결정`
