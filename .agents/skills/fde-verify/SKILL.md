# S6 검증 (130–148분)

## 역할
이 스킬은 만든 쪽의 가정을 모르는 검토자로서, 합의된 기준이 실제 화면에서 충족되는지 판정한다. 채점은 실행 화면과 코드·커밋·대화 기록을 대조한다.
사람이 정하는 것: 처음 쓰는 사용자처럼 직접 써 보기, 무엇을 고칠지(첫 세션에서), 담당자 결과 보고와 수용 확인.

## 입력
`docs/AGREEMENT.md`(한 줄 명세·만들 것·제약·성공 기준·확인 방법), `docs/INTERVIEW.md` "정리" 절(담당자 인용만 — 만든 쪽의
해석이 아니다), README 또는 HANDOFF의 실행 명령·포트. DECISIONS는 판정을 마친 뒤에만 읽는다.

## 절차
검수는 **형식 → 의미 → 목적** 순서로, 섞지 않는다. 앞 단계가 막히면 뒤 단계로 가지 않는다(멈출 기준이 완벽보다 먼저).

1. **형식 — 쓸 수 있는 상태인가**:
   - 실행: `START_CMD="<실행 명령>" PORT=<포트> bash .agents/skills/fde-verify/scripts/verify.sh /` — localhost 바인딩 경고는 1순위 문제.
   - 키·URL 하드코딩, `.env` 커밋: `git log -p | grep -iE "sk-|OPENAI_API_KEY="`
   - README의 필수 제출 파일이 실제 경로에 있는가
   - **앱이 뜨지 않으면 여기서 멈춘다** — 의미·목적 판정을 하지 않고 "실행 불가"를 1순위 문제로 보고한다.
2. **의미 — 합의한 대로 동작하는가**: 성공 기준을 하나씩 **"확인 방법" 열대로** 대조해 VERIFY "성공 기준별 충족" 표에 적는다.
   확인 방법이 비어 있으면 네 해석으로 확인하고 "확인 방법 없음"을 문제 목록에 올린다. 함께 본다:
   - LLM 실패·지연 시 화면, 빈 입력·아주 긴 입력, 새로고침 후 데이터
   - 처음 쓰는 사람이 설명 없이 **첫 화면 → 결과까지 3번 안의 조작**으로 가는가, 입력 중·처리 중·실패가 글자로 보이는가
3. **목적 — 담당자의 일에 맞는가**: 결과 화면을 INTERVIEW 인용과 대조해 VERIFY "목적 적합" 표에 적는다.
   - 한 줄 명세의 [어떤 문제]를 이 결과가 실제로 줄이는가(목표(왜) 인용)
   - L1 기준이 결과에 지표로 보이는가 / L2 순서·개수대로 나오는가 / L3 어조가 묻어나는가
   - AGREEMENT "제약"을 어기는 저장·전송이 없는가
4. (판정 후) DECISIONS·VERIFY 내용이 코드·커밋과 맞는가, 의도 칸이 빈 결정. STATE 복귀 지점 SHA가 `git log`에 있는가.
5. 문제 목록을 심각도순으로, 항목마다 "15분 안에 고칠 수 있음/없음"과 어느 단계(형식/의미/목적)에서 나왔는지.

재검증은 첫 세션이 고친 항목만, **1회**. 그 뒤에도 남은 문제는 DECISIONS "알려진 약점"으로 넘기고 S7로 간다.

## 출력
```text
VERIFY "성공 기준별 충족": | 성공 기준 | 충족|부분|미충족 | 근거(파일:줄 또는 실행 결과) |  — 성공 기준 수만큼
VERIFY "목적 적합": | 목표(왜) · L1 · L2 · L3 · 제약 | 반영|부분|미반영|인용 없음 | 근거(화면 결과 ↔ INTERVIEW 인용) |  — 정확히 5행
문제 목록: <심각도> · <형식|의미|목적> · <문제 한 줄> · <근거> · 15분 가능|불가
```
불변 조건: 성공 기준마다 정확히 한 행. 근거가 없는 판정은 "부분"을 넘지 않는다. 형식 단계에서 앱이 뜨지 않았으면 두 표는 비우고 문제 목록만 낸다.

## 원칙
1. 근거는 실행 결과나 파일:줄로 적는다.
2. 판정이 끝난 뒤에 만든 쪽 문서(DECISIONS)를 대조한다.
3. 성공 기준을 다 채워도 목적이 어긋날 수 있다(기준이 좁게 쓰였을 때). 그래서 목적 단계를 따로 둔다.

## 금지사항
- 코드를 고치지 않는다.
- 실행하지 않은 것을 "충족"으로 적지 않는다.
- 키·URL 값을 출력하지 않는다.

## 확인요청
- 실행 명령·포트를 모르면 README·HANDOFF를 보고, 그래도 없으면 사람에게 묻는다.

## 예시
### 입력
```
AGREEMENT 성공 기준 2: "결과 화면에 고칠 점이 한 가지만 보인다" / 확인 방법: "텍스트 입력에 40초 분량 답변 → 결과 화면의 '고칠 점' 항목 수"
```
### 출력
```text
| 2. 결과 화면에 고칠 점이 한 가지만 보인다 | 부분 | 텍스트 입력 경로에서 1개 확인(실행). 음성 경로는 마이크 차단으로 미확인 |
목적 적합: | L3 | 미반영 | 결과 문장 "답변 속도를 개선하세요" ↔ INTERVIEW L3 "숨 한 번 쉬고 가셔도 돼요" — 담당자 어조 아님 |
문제 목록: 중 · 의미 · 음성 경로 결과 미확인 · Browser 미리보기 마이크 권한 거부 · 15분 불가
문제 목록: 중 · 목적 · 피드백 어조가 일반론 · 위 L3 행 · 15분 가능(프롬프트 예시에 L3 인용 추가)
```

## 인접 스킬
- vs `$fde-build`: build는 만든 세션의 항목 확인, 이 스킬은 별도 세션의 전체 판정.
- 다음: 첫 세션이 "15분 가능" 1순위만 고친 뒤 `$fde-submit`.

## 완료
- 성공 기준 표와 목적 적합 표가 다 찼고(또는 형식 단계에서 멈춘 이유가 있고) 문제마다 15분 가능 여부가 있다. 148분이 되면 채운 데까지 보고.
- 자가 검증: 성공 기준 표 행 수 = AGREEMENT 성공 기준 수, 목적 적합 표 5행, 모든 행에 근거가 있다.
