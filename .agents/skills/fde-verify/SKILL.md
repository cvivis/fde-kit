# S6 검증 (130–148분)

## 역할
이 스킬은 만든 쪽의 가정을 모르는 검토자로서, 합의된 기준이 실제 화면에서 충족되는지 판정한다. 채점은 실행 화면과 코드·커밋·대화 기록을 대조한다.
사람이 정하는 것: 처음 쓰는 사용자처럼 직접 써 보기, 무엇을 고칠지(첫 세션에서), 담당자 결과 보고와 수용 확인.

## 입력
`docs/AGREEMENT.md`(한 줄 명세·만들 것·제약·성공 기준·확인 방법), `docs/INTERVIEW.md` "정리" 절(담당자 인용만 — 만든 쪽의
해석이 아니다), `docs/REQ-TASK.md`·`docs/REQ-USER.md`의 범위 "이번" 행(요구 원문·종류·설계 연결), README 또는 HANDOFF의 실행 명령·포트.
DECISIONS는 판정을 마친 뒤에만 읽는다.

## 절차
검수는 **형식 → 의미 → 목적** 순서로, 섞지 않는다. 앞 단계가 막히면 뒤 단계로 가지 않는다(멈출 기준이 완벽보다 먼저).

1. **형식 — 쓸 수 있는 상태인가**:
   - 실행: `START_CMD="<실행 명령>" PORT=<포트> bash .agents/skills/fde-verify/scripts/verify.sh /` — localhost 바인딩 경고는 1순위 문제.
   - 키·URL 하드코딩, `.env` 커밋: `git log -p | grep -iE "sk-|OPENAI_API_KEY="`
   - README의 필수 제출 파일이 실제 경로에 있는가(원본 파일에 쓰는 제출물은 STATE "제출 복사본"의 `submission/` 경로). 과제 원본 파일이 그대로인가(`check-stage.sh S6`)
   - **앱이 뜨지 않으면 여기서 멈춘다** — 의미·목적 판정을 하지 않고 "실행 불가"를 1순위 문제로 보고한다.
2. **의미 — 합의한 대로 동작하는가**: 성공 기준을 하나씩 **"확인 방법" 열대로** 대조해 VERIFY "성공 기준별 충족" 표에 적는다.
   확인 방법이 비어 있으면 네 해석으로 확인하고 "확인 방법 없음"을 문제 목록에 올린다. 함께 본다:
   - LLM 실패·지연 시 화면, 빈 입력·아주 긴 입력, 새로고침 후 데이터
   - 처음 쓰는 사람이 설명 없이 **첫 화면 → 결과까지 3번 안의 조작**으로 가는가, 입력 중·처리 중·실패가 글자로 보이는가
   - 화면(단계)마다 할 일이 하나이고 보이는 것이 3묶음 이하인가, 기록·설정이 접혀 있거나 다른 화면인가(S3 화면 표와 대조)
   **요구 ID 단위 충족표**: 범위 "이번" 요구마다 실제로 실행해 보고 VERIFY 첫 표에 S6 행(시각·요구 ID·명령·결과)을 남긴 뒤 REQ "구현 확인" 칸을
   `충족|부분|미충족 — VERIFY <시각> S6` 또는 ``충족|부분|미충족 — S6 `<명령>` → <결과>``로 다시 쓴다(S4 판정은 VERIFY 행에 남아 있다).
   반드시 요구의 충족은 검사기 출력(`검사 n · 위반 0`)이 그 근거에 있어야 한다. 확인하지 못한 요구는 비워 두어 미확인으로 남긴다. 이어
   `bash .agents/skills/fde-start/scripts/check-req.sh verify` 출력 한 줄을 VERIFY "요구별 충족"에 적고, 미확인 ID(근거 없는 판정 포함)와 코드에 없는 요구 숫자를 문제 목록에 올린다.
   판정 근거가 있는지·개수는 스크립트가 센다 — 손으로 다시 세지 않는다.
3. **목적 — 담당자의 일에 맞는가**: 결과 화면을 INTERVIEW 인용과 대조해 VERIFY "목적 적합" 표에 적는다.
   - 한 줄 명세의 [어떤 문제]를 이 결과가 실제로 줄이는가(목표(왜) 인용)
   - L1 기준이 결과에 지표로 보이는가 / L2 순서·개수대로 나오는가 / L3 어조가 묻어나는가
   - AGREEMENT "제약"을 어기는 저장·전송이 없는가
   - `docs/LOGIC.md`에 결정이 있으면 `bash .agents/skills/fde-start/scripts/check-work.sh build`를 한 번 돌려 `검사기:`·`위반 테스트:` 줄을 VERIFY에 옮긴다
     (검사기를 따로 손으로 돌리지 않는다). 반드시 조건 위반이 있으면 의미 문제로 올린다. 위반 테스트가 없거나 실패면 그 검사기의 "위반 0"은 충족 근거가 아니다.
     같은 출력의 완료 항목·복귀 지점 줄은 절차 4에 쓴다.
   - **과대해석(구현 뒤)**: `check-req.sh links`의 "근거 없음(범위 밖)"·"해석 차이"와, 화면 기능·코드의 규칙(한도·필터·예외 처리)을 요구 원문과
     비교해 숫자·대상·조건이 넓어지거나 좁아진 것을 VERIFY "해석 점검"에 시점 S6으로 적는다. 고칠지는 사람이 정한다 — 사람 판단 칸은 비워 두고 문제 목록에 올린다.
4. (판정 후) DECISIONS·VERIFY 내용이 코드·커밋과 맞는가, 의도 칸이 빈 결정. 완료 항목마다 VERIFY 행·커밋이 있는지와 복귀 지점 SHA는
   `check-work.sh build`의 완료 항목·복귀 지점 줄을 그대로 쓴다(`실패:` 줄은 문제 목록에).
5. 문제 목록을 심각도순으로, 항목마다 "15분 안에 고칠 수 있음/없음"과 어느 단계(형식/의미/목적)에서 나왔는지.
6. AGREEMENT "수용 확인"이 양식 placeholder(`(팀장 피드백 그대로)`) 그대로면, 사람에게 결과 보고(템플릿 5)를 보냈는지 묻는다.
   보냈고 답이 없으면 "요청했으나 응답을 받지 못함"을, 안 보냈으면 "아직 전달 전"을 그 자리에 적게 한다 — 빈 placeholder로 S7에 넘기지 않는다.
7. STATE 기준판에 "모의 상태"가 적혀 있는데 S0에서 OpenAI 환경변수가 "설정됨"이었다면, 그 핵심 기능은 "충족"으로 올리지 않고
   문제 목록에 1순위로 올린다(의미 단계). 환경변수가 "없음"이어도 실제 AI가 필요한 기준은 "부분/미충족"과 제약 사유를 남긴다.
   모의로 확인한 UI·스키마 순서 같은 독립 기준만 해당 증거 범위에서 충족으로 판정한다.

재검증은 첫 세션이 고친 항목만, **1회**. 그 뒤에도 남은 문제는 DECISIONS "알려진 약점"으로 넘기고 S7로 간다.

## 출력
```text
VERIFY "성공 기준별 충족": | 성공 기준 | 충족|부분|미충족 | 근거(파일:줄 또는 실행 결과) |  — 성공 기준 수만큼
REQ "구현 확인" 칸: 충족|부분|미충족 — VERIFY <시각> S6 | — S6 `<명령>` → <결과>  — 범위 "이번" 요구마다, 확인 못 한 요구는 빈칸(미확인)
VERIFY 검사기: check-work.sh build 출력의 "검사기: 검사 n · 위반 m"·"위반 테스트: …" 줄 그대로
VERIFY "요구별 충족": - verify 결과: 구현 확인: 요구 n개 중 구현 확인 m개(충족 a · 부분 b · 미충족 c), 미확인: <ID 또는 없음>
VERIFY "해석 점검": | S6 | <대상·위치> | <요구 ID 또는 없음> | 근거 없음|넓힘|좁힘|종류 바뀜 | <요구 원문 ↔ 구현> | (사람) |
VERIFY "목적 적합": | 목표(왜) · L1 · L2 · L3 · 제약 | 반영|부분|미반영|인용 없음 | 근거(화면 결과 ↔ INTERVIEW 인용) |  — 정확히 5행
문제 목록: <심각도> · <형식|의미|목적> · <문제 한 줄> · <근거> · 15분 가능|불가
```
불변 조건: 성공 기준마다 정확히 한 행. 근거가 없는 판정은 "부분"을 넘지 않는다. 미확인 요구는 개수·ID가 문제 목록에 있다(숨기지 않는다).
검사한 수가 0건인 근거(테스트 0개 수집, 검사기 `검사 0건`, 빈 결과)는 "충족" 근거로 쓰지 않는다. 형식 단계에서 앱이 뜨지 않았으면 두 표는 비우고 문제 목록만 낸다.

## 원칙
1. 근거는 실행 결과나 파일:줄로 적는다.
2. 판정이 끝난 뒤에 만든 쪽 문서(DECISIONS)를 대조한다.
3. 성공 기준을 다 채워도 목적이 어긋날 수 있다(기준이 좁게 쓰였을 때). 그래서 목적 단계를 따로 둔다.

## 금지사항
- 코드를 고치지 않는다.
- 실행하지 않은 것을 "충족"으로 적지 않는다.
- 키·URL 값을 출력하지 않는다.

## 확인요청
- 실행 명령·포트를 모르면 README·HANDOFF를 보고, 그래도 없으면 사람에게 묻는다.
- 해석 점검(근거 없음·넓힘·좁힘) 행은 고칠지 묻는 질문으로 문제 목록에 올린다 — 결정은 사람이 한다.

## 예시
### 입력
```
AGREEMENT 성공 기준 2: "결과 화면에 고칠 점이 한 가지만 보인다" / 확인 방법: "텍스트 입력에 40초 분량 답변 → 결과 화면의 '고칠 점' 항목 수"
```
### 출력
```text
| 2. 결과 화면에 고칠 점이 한 가지만 보인다 | 부분 | 텍스트 입력 경로에서 1개 확인(실행). 음성 경로는 마이크 차단으로 미확인 |
목적 적합: | L3 | 미반영 | 결과 문장 "답변 속도를 개선하세요" ↔ INTERVIEW L3 "숨 한 번 쉬고 가셔도 돼요" — 담당자 어조 아님 |
문제 목록: 중 · 의미 · 음성 경로 결과 미확인 · Browser 미리보기 마이크 권한 거부 · 15분 불가
문제 목록: 중 · 목적 · 피드백 어조가 일반론 · 위 L3 행 · 15분 가능(프롬프트 예시에 L3 인용 추가)
```

## 인접 스킬
- vs `$fde-build`: build는 만든 세션의 항목 확인, 이 스킬은 별도 세션의 전체 판정.
- 다음: 첫 세션이 "15분 가능" 1순위만 고친 뒤 `$fde-submit`.

## 완료
- 성공 기준 표와 목적 적합 표가 다 찼고(또는 형식 단계에서 멈춘 이유가 있고) 문제마다 15분 가능 여부가 있다. VERIFY "요구별 충족"에 verify 결과 한 줄이 있다. 148분이 되면 채운 데까지 보고.
  AGREEMENT "수용 확인"에 placeholder가 남아 있지 않다(절차 6).
- STATE 진행 측정에 S6 종료 시각·확인 가능한 토큰을 한 행 남긴다. 전체 테스트는 검증에 필요한 범위로 한 번 수행한다.
- 자가 검증은 스크립트로 한다: `bash .agents/skills/fde-start/scripts/check-work.sh verify`가 통과한다(성공 기준 표 행 수 = AGREEMENT 성공 기준 수,
  행마다 판정·근거, 검사 0건 근거의 충족 없음, 목적 적합 5행 판정·근거, verify 결과 줄). 행 수를 손으로 세지 않는다.
  성공 기준 표가 0행이면 완료가 아니다(앱이 뜨지 않아 멈춘 경우만 예외이며 문제 목록에 이유가 있다 — 이때 스크립트 실패를 그대로 보고한다).
