# 현업 기준 추출 — 3층 프로토콜과 도메인 적응

담당자가 **말로만 가지고 있는 판단 기준**을 캐내 구현 위치로 보내는 절차.
도메인과 무관하게 작동한다. S1에서 사람이 쓰고, S3에서 설계 입력이 된다.

## 0. 요구 두 종류를 먼저 가른다

요청 문장(보통 1~2문장)에는 성격이 다른 요구가 섞여 있다.

| 종류 | 알아보는 법 | 변별력 |
|---|---|---|
| **R-명시** | 요청서·지문에 이미 설명돼 있다 | 없다. 누구나 만든다 |
| **R-암묵** | *"제가 / 저희가 ~하는 **방식·기준·순서**도 담고 싶다"* | ★ 여기서 갈린다 |

**R-암묵을 찾는 방법**: 요청 문장에서 "제가/저희가 ~하는" + 방식·기준·순서·느낌을 가리키는 명사를
찾는다. 그 명사가 **추출 대상**이다. 없으면 요청서가 비워 둔 "정해지지 않은 것" 중
**판단 기준이 필요한 항목**이 같은 역할을 한다.

R-암묵은 **묻지 않으면 절대 나오지 않는다.** 담당자는 자기 기준을 의식하지 못하거나, 너무
당연해서 말할 생각을 안 한다.

## 1. 3층 추출 프로토콜

"방식"은 기준 하나가 아니라 **세 층**이고, 각 층이 구현의 다른 부분이 된다.

| 층 | 캐내는 것 | 질문 형태 | 어디로 가나 |
|---|---|---|---|
| **L1 기준** | 볼 때 **먼저 보는 것**, 좋은 것/아쉬운 것을 가르는 변수 | "좋은 ○○와 아쉬운 ○○를 어떻게 구분하세요? 가장 먼저 보시는 건요?" | **고정 코드 지표** + 출력 항목 이름 |
| **L2 구조** | **어떤 순서로, 몇 개까지** 말하는가 | "의견 주실 때 어떤 순서로 말씀하세요? 한 번에 몇 가지까지 짚으세요?" | **출력 스키마 필드 순서 + 화면 배치** |
| **L3 어휘** | 실제로 쓰는 **문장 원문** | "그때 실제로 하신 말을 문장 그대로 기억하세요?" | **LLM 프롬프트의 어조 예시(few-shot)** |

**L2가 가장 과소평가된다.** "좋은 점 먼저 → 고칠 것 하나 → 다음 할 일 하나"처럼 순서와 개수가
정해지면 그게 곧 **JSON 스키마**이고 **화면 레이아웃**이다. 그리고 "한 번에 세 가지 넘게 말하면
기억하지 못한다" 같은 현업 제약이 나오면 **그게 성공 기준이 된다** — 검증 가능하고 화면에서 바로
확인된다.

**L3이 품질을 직접 바꾼다.** "말이 빠르셨어요"와 "조금만 천천히, 숨 한 번 쉬고 가셔도 돼요"는
같은 지적이지만 받는 사람에게 닿는 정도가 다르다. 담당자 문장 2~3개를 프롬프트 예시로 넣으면
출력 어조가 거기로 수렴한다. **이것이 "현업의 방식을 담는다"의 기술적 실체다.**

## 2. 10줄 질문 뼈대 — 외울 것은 이것뿐

`○○`에 추출 대상(결과물·산출물·업무)을, `△△`에 담당자가 쓴 모호어를, `××`에 뺄 후보 기능을 넣는다.

```
[지도]   "제가 이 업무를 잘 몰라서요. 어떤 걸 여쭤보면 도움이 될까요?"
[장면]   "가장 최근에 ○○하셨던 날, 처음부터 끝까지 어떻게 진행됐나요?"
[왜]     "그 일이 제대로 안 되면 어떻게 되나요?"
[L1]     "좋은 ○○와 아쉬운 ○○를 어떻게 구분하세요? 가장 먼저 보시는 건요?"
[L2]     "의견을 주실 때 어떤 순서로 말씀하세요? 한 번에 몇 가지까지 짚으세요?"
[L3]     "그때 실제로 하신 말을 문장 그대로 기억하세요?"
[모호어] "'△△'라고 하셨는데, ⓐ인지 ⓑ인지 ⓒ인지 어느 쪽에 가까울까요?"
[정량]   "얼마나 자주, 한 번에 몇 분, 몇 명이 쓰나요?"
[성공]   "이게 잘 됐다는 건 무엇을 보고 아실 것 같으세요?"
[거절]   "만약 ××는 없고 ○○만 된다면, 업무에 쓸 만하실까요?"
```

[왜]·[성공]·[거절]은 요구를 **목표(안 되면 무엇을 잃나) / 성공 판단(무엇을 보고 아나) / 상쇄(무엇을 포기해도 되나)**
세 칸으로 받는 질문이다. L1~L3이 "담당자의 방식"이라면 이 세 칸은 "무엇을 왜 만드나"다 — 합의문 한 줄 명세의
[어떤 문제], 성공 기준, "안 만들 것"의 이유가 여기서 인용으로 나온다. 비어 있으면 S2가 추측으로 채우게 된다.

순서 규칙 세 개:

1. **[지도]를 먼저.** "제가 뭘 여쭤보면 될까요"는 답할 수 있는 범위를 받아내는 질문이다.
   반대로 "제가 할 걸 하나, 둘, 셋 알려주세요"는 가장 나쁜 질문이다.
2. **[L1]→[L2]→[L3]을 연속으로.** 주제를 바꾸지 않고 같은 자리를 세 번 파는 것이
   새 주제로 넘어가는 것보다 수익이 크다. 이 3연속이 S1의 최고 가치 구간이다.
3. **[거절]을 마지막에.** 범위 축소를 S2가 아니라 **S1 안에서 사전 동의**로 받는다.
   "그 정도면 충분해요"를 받으면 합의문의 "안 만들 것"에 인용이 생긴다.

1라운드 전체 순서(지도·장면·기준·우회·정량·환경·성공·경계)는 `question-bank.md`를 본다.

### 답을 받은 뒤 같은 자리를 더 파는 5수

새 주제로 넘어가기 전에 쓴다. 주제를 바꾸는 것보다 수익이 크다.

| 패턴 | 형태 | 얻는 것 |
|---|---|---|
| 극단 | "그중에 제일 심했던 경우는 어땠나요?" | 요구의 상한 → 임계값 |
| 반례 | "반대로 잘 됐던 때는 뭐가 달랐나요?" | 좋음/아쉬움을 가르는 **실제 변수** |
| 문장 그대로 | "그때 하신 말을 문장 그대로 기억하세요?" | **L3** (가장 수익이 크다) |
| 빈도 쪼개기 | "10번 중 몇 번쯤인가요?" | 우선순위 근거 (3개로 줄일 때) |
| 거절 확인 | "××는 없고 ○○만 되면 쓸 만하실까요?" | **범위 축소의 사전 동의** |

## 3. 도메인 적응 절차 — 5분 (S0 끝 ~ S1 시작)

질문 세트는 미리 만들어 가는 것이 아니라 **요청서에서 만든다.**

| 단계 | 하는 일 | 산출 |
|---|---|---|
| 1 (60초) | 요청 문장에서 **R-명시 / R-암묵**을 가른다 | 변별 요구 1개 |
| 2 (60초) | R-암묵의 명사를 `○○`에 대입 | L1·L2·L3 질문 3개 |
| 3 (60초) | "정해지지 않은 것" 각 항목을 **모호어 해체** 질문으로 | 2~3개 |
| 4 (60초) | 요청서에 **없는 숫자**를 목록화(길이·빈도·인원·임계값) | 정량 질문 1~2개 |
| 5 (60초) | 앞에 [지도]·[장면]·[왜], 뒤에 [성공]·[거절]을 붙인다 | 최종 10~12개, 순서 확정 |

**요청서에 숫자가 없는 것이 기본값이다.** 검증 가능한 성공 기준을 쓰려면 숫자를 인터뷰에서
받아야 한다. 4단계를 건너뛰면 성공 기준이 "잘 된다" 수준에서 멈춘다.

## 4. 번역표 — 캐낸 것을 어디로 보내나

담당자의 말을 **형태로** 분류한다. 내용이 아니라 형태가 목적지를 정한다.

| 담당자가 말한 형태 | 번역 | 들어가는 곳 |
|---|---|---|
| "○○가 너무 많다 / 적다" | 개수·빈도 카운트 | **고정 코드** 지표 |
| "너무 길다 / 짧다" | 길이 임계값 (정량 질문의 숫자) | **고정 코드** 판정 + 성공 기준 |
| "○○면 아예 안 된다" | 하드 거부 조건 | **고정 코드** 판정 (LLM 호출 전에 걸러낸다) |
| "○○가 꼭 들어가야 한다" | 요소 포함 여부 | **LLM** 판단 → 스키마 boolean |
| "좋은 것 먼저, 고칠 건 하나만" | 출력 순서·개수 | **스키마 필드 순서 + 화면 배치** |
| "'~하셔도 돼요'라고 말한다" | 어조·표현 | **LLM 프롬프트 어조 예시** |

**규칙 하나: 셀 수 있는 것은 전부 고정 코드로 내린다.**
LLM에게 숫자를 물으면 값이 흔들리고, 같은 입력을 두 번 넣으면 다른 값이 나온다. 반대로
"○○가 들어갔나" 같은 의미 판단은 고정 코드로 못 하므로 LLM에 맡기고 **스키마로 받는다.**
이 경계가 `AGENTS.md` 원칙 3의 실제 적용이고, "왜 이렇게 나눴나"의 준비된 답이 된다.

## 5. LLM 프롬프트에 넣는 방법

```
system: 너는 <담당자 역할>이다.
        기준: {L1에서 받은 기준 원문}
        방식: {L2에서 받은 순서·개수} — 이 순서와 개수를 벗어나지 마라.
        어조 예시: {L3에서 받은 문장 2~3개}
        기준에 없는 평가는 하지 마라.
        숫자 지표는 이미 계산되어 주어지므로 다시 계산하지 마라.
user:   입력: {사용자 입력}
        지표(고정 코드 계산): {지표 이름과 값}
```

마지막 두 줄이 핵심이다. **지표를 주되 다시 계산하지 말라고 못 박는다.** 그러면 LLM은 숫자를
사실로 받아들여 **문장만** 만든다. 숫자의 출처가 하나로 고정되고, 화면의 숫자와 설명 문장이
어긋나는 사고가 사라진다.

프롬프트에 넣은 담당자 문장은 **출처를 `DECISIONS.md`에 남긴다**(어느 질문의 답인지).
평가자나 인수자가 프롬프트를 읽고 "이 문장은 어디서 왔나"를 물을 수 있다.

## 6. 흔한 실패 3개

1. **"전문가처럼 평가해 줘"로 끝낸다.** 담당자의 방식이 아니라 모델의 일반론이 나온다.
   "이 담당자의 기준이 어디에 반영됐나"에 답할 수 없다 — 가장 흔한 감점.
2. **가설을 사실처럼 쓴다.** 도메인 상식으로 추측한 기준을 합의문 근거로 올리면, 인용이 없어
   추적이 안 된다. 가설은 **확인 질문과 짝으로만** 존재한다.
3. **담당자에게 기술을 묻는다.** "어떤 식으로 만들까요?"는 역할 경계 위반이다. 되돌리는 문장:
   "제가 방법은 찾아보겠습니다. 다만 보시기에 '이건 됐다' 싶은 상태가 어떤 모습일지만 알려주세요."
